# 需求规格说明书 / PRD 生成技能

基于「AI赋能项目管理：特定行业/项目的需求规格说明书的关键组件生成」（2601课程案例第155篇）的方法论，支持为任意行业、任意项目生成规范的需求规格说明书或PRD文档，含需求矩阵、用例图和用例描述。

## 触发场景

当用户表达以下意图时应用本技能：
- 需要生成/编写需求规格说明书
- 需要编写 PRD、产品需求文档
- 提及「需求规格说明书」「PRD」「Product Requirements Document」
- 需要需求矩阵、用例图、用例描述
- 需要基于模板填充需求相关内容

## 工作流程

### 第一步：互动式信息收集

在生成需求规格说明书之前，**必须先以对话方式收集**以下必要信息。若用户未一次性提供，则逐项询问：

#### 必填信息

| 信息项 | 说明 | 示例 |
|--------|------|------|
| **项目名称** | 项目/系统的正式名称 | 基于RAG的AI智能客服系统 |
| **系统上下文** | 本系统与哪些系统交互、交互方式 | 与企业微信集成、与知识库 API 对接 |
| **功能性需求** | 系统应实现的核心功能列表 | 智能问答、知识库管理、会话记录 |
| **非功能性需求** | 性能、安全、可用性等要求 | 响应时间 &lt;3秒、支持 7×24 运行 |

#### 建议收集的扩展信息

| 信息项 | 说明 | 是否必填 |
|--------|------|----------|
| 行业/领域 | 项目所属行业 | 建议必填 |
| 目标用户 | 系统主要使用对象 | 建议必填 |
| 系统边界与范围 | 系统包含/不包含的功能范围 | 建议必填 |
| 运行环境 | 部署环境、硬件/软件依赖 | 建议必填 |
| 约束条件 | 技术、合规、工期等约束 | 按需 |
| 术语与缩写 | 领域内专用术语定义 | 按需 |
| 参考资料 | 关联的法规、标准、上级文档 | 按需 |
| 用例参与者 | 与系统交互的角色（如：客服人员、管理员） | 建议必填 |

#### 一次性录入表单

若用户希望一次性提供全部信息，可引导其按以下格式填写（支持复制粘贴或逐条回答）：

```
【需求规格说明书 / PRD 信息录入单】

一、基础信息
- 项目名称：
- 行业/领域：
- 编制单位/部门：
- 版本号（如 V1.0）：
- 编制日期：

二、系统上下文
- 关联系统名称及说明：
- 交互方式（API、消息队列、文件导入等）：
- 系统边界与范围（含/不含）：
- 目标用户（角色）：
- 运行环境：

三、功能性需求
- 功能模块1（名称及简要描述）：
- 功能模块2：
- 功能模块3：
（可扩展，每行一条，格式：FR-XX：功能描述）

四、非功能性需求
- 性能（响应时间、并发量等）：
- 可用性（7×24、SLA 等）：
- 安全性（认证、授权、数据加密等）：
- 可维护性/可扩展性：
- 合规性（如有）：
（可扩展，格式：NFR-XX：描述）

五、约束条件
- 技术约束：
- 工期/资源约束：
- 合规约束：

六、术语与缩写（可选）
- 术语1：定义
- 术语2：定义

七、用例参与者
- 参与者1（如：客服人员）：
- 参与者2（如：系统管理员）：
- 参与者3：

八、其他补充
- 参考资料：
- 特殊说明：
```

#### 一次性录入 UI

本技能目录下的 [input-form.html](input-form.html)，用户可在浏览器中打开、填写后点击「生成可复制文本」，将结果粘贴到 Cursor 对话中，实现一次性录入。

### 第二步：确定输出格式

1. **用户提供自定义 Word 格式**：若用户上传或指定了公司/客户的 Word 模板（.docx），则严格按照该模板的章节结构、样式、标题层级输出。
2. **默认格式**：若用户未提供自定义格式，则按照「基于RAG的AI智能客服项目的交付样例」的结构和层级输出，包含需求矩阵、用例图和用例描述。完整结构见 [reference.md](reference.md)。

### 第三步：生成需求规格说明书

1. 依据收集到的信息，按选定格式填充各章节内容。
2. **需求矩阵**：生成需求追溯矩阵表，包含需求ID、需求描述、类型（功能/非功能）、优先级、关联用例等列。
3. **用例图**：以 Mermaid 或文字形式描述用例图，体现参与者与用例的对应关系。
4. **用例描述**：对主要用例给出结构化描述（用例名称、参与者、前置条件、主流程、备选流程、后置条件、关联需求ID）。
5. 行业术语、技术描述应与用户所述行业一致，避免泛泛而谈。
6. 若信息不足，对缺失条目标注「[待补充：XXX]」，并提示用户后续补充。

### 第四步：输出与修订

1. **输出格式**：优先生成 `.docx` 文件；若不支持直接生成 Word，则输出结构完整、表格清晰的 Markdown，便于用户复制到 Word。
2. **中文表述**：全文使用中文，避免错别字、乱码；数字、单位、日期格式符合中文习惯。
3. 若用户需调整某部分，根据反馈单独修订并保持整体一致。

## 需求规格说明书核心结构（默认）

默认采用「基于RAG的AI智能客服项目交付样例」的结构，包含以下部分：

1. **引言**  
   - 目的、范围、定义、参考资料

2. **总体描述**  
   - 产品概述、系统上下文、用户特征、运行环境、约束

3. **功能性需求**  
   - 按模块/特性组织的详细功能描述

4. **非功能性需求**  
   - 性能、可用性、安全性、可维护性等

5. **需求矩阵**  
   - 需求ID | 需求描述 | 类型 | 优先级 | 关联用例

6. **用例图**  
   - 参与者与用例关系的图/描述

7. **用例描述**  
   - 用例名称、参与者、前置条件、主流程、备选流程、后置条件、关联需求

详细字段说明与示例见 [reference.md](reference.md)。

## 注意事项

1. **不臆造**：未收集到的具体需求、参与者、约束等，不得编造，应标注待补充或使用占位符。
2. **行业适配**：政务类强调合规、数据安全；金融类强调审计、风控；医疗类强调隐私、监管；企业应用可侧重易用性与集成。
3. **逻辑闭环**：需求 → 需求矩阵 → 用例 → 用例描述，保持追溯关系完整。
4. **格式规范**：标题层级清晰（一级、二级、三级），表格结构完整，用例描述结构统一，便于在 Word 中进一步排版。
